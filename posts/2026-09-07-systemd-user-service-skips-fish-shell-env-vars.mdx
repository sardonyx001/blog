# A systemd --user service won't see env vars exported by your fish config

I was setting up [Hermes Agent](https://hermes-agent.nousresearch.com/) on a VPS as an always-on Discord bot, wired up to use my existing Claude subscription instead of a separate API key. Testing it from the CLI over SSH worked perfectly. The moment I actually messaged the bot on Discord, it replied:

```text
⚠️ Provider authentication failed. Check the configured credentials; raw provider details are in the gateway logs.
```

Classic "works on my machine, fails in the service" bug.

## Why the CLI worked but the service didn't

Hermes can auto-detect Claude Code's OAuth credentials so you don't need a separate `ANTHROPIC_API_KEY` — either from the `~/.claude/.credentials.json` file, or from a `CLAUDE_CODE_OAUTH_TOKEN` environment variable if one is set. `hermes auth list` showed both were technically available:

```text
anthropic (2 credentials):
  #1  CLAUDE_CODE_OAUTH_TOKEN oauth   env:CLAUDE_CODE_OAUTH_TOKEN ←
  #2  claude_code          oauth   claude_code
```

The `←` marks which one Hermes actually prefers — the env var, if present. And it *was* present, every time I ran `hermes` interactively over SSH:

```bash
ssh marsa 'env | grep CLAUDE_CODE_OAUTH_TOKEN'
# CLAUDE_CODE_OAUTH_TOKEN=sk-ant-oat01-...
```

Turns out it was set with fish's `set -gx` in `~/.config/fish/config.fish`:

```fish
set -gx CLAUDE_CODE_OAUTH_TOKEN sk-ant-oat01-...
```

That line only runs when an interactive (or `fish -l`) shell starts. My SSH session was launching fish as a login shell, so every command I ran picked it up — `hermes -z 'ping'`, `hermes doctor`, all of it. But Hermes's Discord gateway was running as a **systemd `--user` service**, started via `hermes gateway install`. systemd user services are spawned by `systemd --user` directly, not by any login shell, so they never source `config.fish`, `.bashrc`, or anything else shell-specific. You can confirm exactly what a unit actually sees with:

```bash
systemctl --user show hermes-gateway -p Environment
```

which showed a clean, minimal `PATH` and a couple of Hermes-internal vars — no `CLAUDE_CODE_OAUTH_TOKEN` in sight. The gateway fell back to credential `#2` (the `~/.claude` file), which apparently doesn't get picked up the same way at gateway startup, and auth failed.

## The fix

Don't rely on shell rc files for anything a systemd service needs. Hermes reads its own `~/.hermes/.env` file directly (both CLI and gateway do), so the fix was just to put the token there too:

```bash
echo "CLAUDE_CODE_OAUTH_TOKEN=sk-ant-oat01-..." >> ~/.hermes/.env
hermes gateway restart
```

After that, `systemctl --user show hermes-gateway -p Environment` still doesn't show it (it's loaded by the app from `.env`, not injected by systemd), but the gateway log confirmed `✓ discord connected` with no auth warnings, and messaging the bot worked.

## The general lesson

If a systemd service (user or system) needs a credential, treat "I exported it in my shell config" as **not set** from the service's point of view. Either:

- put it in the app's own env-file mechanism (`.env`, `EnvironmentFile=` in the unit, etc.), or
- put it directly in the systemd unit with `Environment=` / `EnvironmentFile=`.

And when debugging "works interactively, fails as a service" for *any* systemd unit, `systemctl --user show <unit> -p Environment` (drop `--user` for system units) is the fastest way to see exactly what environment the process actually got — no guessing based on what your shell has.
