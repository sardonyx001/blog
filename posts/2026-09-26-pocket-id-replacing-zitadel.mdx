# How to set up Pocket ID: passkey login for your self-hosted apps

If you're running a handful of self-hosted apps on a VPS or home server, you've probably
felt this pain: every app wants its own login, its own password, its own "forgot
password" flow. The fix is single sign-on (SSO) — log in once, get into everything.

The usual SSO tools (Keycloak, Authentik, Zitadel) are built for companies with hundreds
of users and complex permission structures. Running one for yourself is like using a
freight truck to move a single box. **Pocket ID** is the opposite: a small, self-hosted
login server built specifically for solo/small homelab use, where you sign in with a
passkey (Face ID, fingerprint, or a security key) instead of a password.

This guide walks through installing it, connecting your first app, and the couple of
gotchas that trip people up.

## What you get

- One login server for all your self-hosted apps.
- No passwords anywhere — you sign in with your phone's Face ID/fingerprint, or a
  password manager that supports passkeys (1Password, Bitwarden, iCloud Keychain, etc.).
- A single container to run: no separate database to manage, everything lives in one
  SQLite file.
- Works with any app or reverse proxy that speaks standard OpenID Connect (OIDC) —
  Caddy, Nginx, Traefik, or the apps' own built-in OIDC support.

## Step 1: Run the container

Pocket ID ships as a single Docker image. Here's a minimal `docker-compose.yml`:

```yaml
services:
  pocketid:
    image: ghcr.io/pocket-id/pocket-id:latest
    container_name: pocketid
    restart: unless-stopped
    environment:
      APP_URL: https://id.yourdomain.com
      TRUST_PROXY: "true"
      ENCRYPTION_KEY: "generate-a-random-32-byte-hex-string-here"
    volumes:
      - ./data:/app/backend/data
    ports:
      - "1411:1411"
```

Two things to get right before you start it:

- **`APP_URL` must be the real public HTTPS URL you'll use.** Passkeys are
  cryptographically tied to the exact domain they were registered on. If you change this
  domain later, every passkey breaks and everyone has to re-register.
- **Generate a real `ENCRYPTION_KEY`.** Any random 32-byte hex string works:
  ```
  openssl rand -hex 32
  ```

Then bring it up:

```
docker compose up -d
```

## Step 2: Put it behind HTTPS

This is not optional. Passkeys use the WebAuthn browser API, which flatly refuses to work
over plain HTTP (with one exception: `localhost`, for local testing). Whatever reverse
proxy you're already using — Caddy, Nginx, Traefik — point a subdomain at the container's
port 1411 with a real TLS certificate.

A minimal Caddy example:

```
id.yourdomain.com {
    reverse_proxy localhost:1411
}
```

Caddy handles the certificate automatically. If you're using Nginx or Traefik, the
concept is the same: real domain, real cert, reverse-proxied to port 1411.

## Step 3: Create your admin account

Visit `https://id.yourdomain.com/setup`. This page is only available until the first
account exists — as soon as you finish signup, it stops working for anyone else, which is
the intended safety behavior. Fill in a username and email, and you'll land on a "set up
your passkey" screen.

**Do this on your phone or laptop, not a text-only automated session** — registering a
passkey requires you to physically approve it with Face ID, a fingerprint, or a hardware
key. Register at least two: one you'll use daily (your phone), and a backup (your laptop,
or a password manager that syncs passkeys) — if you only ever have one passkey and lose
that device, recovery is a manual admin process.

## Step 4: Register your first app

Every app that wants to use Pocket ID for login needs its own OIDC "client" registered in
the admin panel. Go to `/settings/admin/oidc-clients` → **Add OIDC Client**.

You'll need to know the callback URL your app or reverse-proxy plugin expects. This
varies by tool:

- **caddy-security** (Caddy's SSO plugin): `https://your-portal-domain/oauth2/<realm-name>/authorization-code-callback`
- **oauth2-proxy**: `https://your-app-domain/oauth2/callback`
- **An app with native OIDC support** (Grafana, Nextcloud, Immich, etc.): check that
  app's own OIDC settings page — it usually shows you the exact callback URL to paste in.

Enter that URL under **Callback URLs**, save, then open the **Credentials** tab and click
**Add client secret**. You now have a Client ID and Client Secret — plug those into
whatever's consuming the login (your reverse proxy config, or the app's own OIDC
settings), along with Pocket ID's discovery URL:

```
https://id.yourdomain.com/.well-known/openid-configuration
```

That single URL is enough for most OIDC clients to auto-discover every endpoint they
need (authorization, token, user info, etc.) — you shouldn't need to hand-enter each one
separately.

## Gotcha: if your reverse proxy fetches config at startup

Some reverse-proxy SSO plugins (Caddy's `caddy-security` is one) try to fetch Pocket ID's
discovery document *while the proxy itself is still starting up* — before its own HTTPS
is even listening. If you point that startup fetch at your public HTTPS domain, you get a
circular dependency: the proxy can't reach itself because it isn't up yet, and it fails
to start entirely.

The fix is to point that specific startup config fetch at Pocket ID's **internal**
address instead of the public one — e.g., if they're both Docker containers on the same
network, `http://pocketid:1411/.well-known/openid-configuration` rather than
`https://id.yourdomain.com/.well-known/openid-configuration`. Everything else (the actual
browser login flow) still goes through the public HTTPS URL as normal — it's only this
one startup-time fetch that needs the internal shortcut.

If your reverse proxy doesn't do a startup-time fetch (most don't), you can skip this
entirely and just use the public URL everywhere.

## Gotcha: callback URL must match exactly

If you ever rename anything — the "realm" name in a Caddy config, the app's domain, the
client name — double check the callback URL registered in Pocket ID still matches exactly
what your proxy/app is sending. A mismatch gives you a clear (if blunt) error:

```
The redirect_uri '...' is not registered for this client.
```

Fix: go back to the OIDC client in Pocket ID's admin panel and update the Callback URL to
match.

## What happens if you lose your device

Since there's no password fallback by design, plan this before you need it:

- **Register two passkeys minimum** (phone + laptop, or phone + a password manager).
- If you're still locked out, an admin can issue a one-time login link from the server:
  ```
  docker exec pocketid /app/pocket-id one-time-access-token <username>
  ```
  This prints a URL valid for one hour that lets you sign in once and register a new
  passkey.

## Should you do this?

If you're the only user (or one of a handful of trusted people) and you're tired of
juggling separate logins for every self-hosted app, yes — it's a small, fast, low-effort
addition. If you need SAML, LDAP sync, or per-app user group permissions for a real team,
Pocket ID intentionally doesn't do that — look at something like Authentik or Keycloak
instead. But for "I want one login for my homelab," it's hard to beat.
