# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

The blog/portfolio powering `jamell.dev` — Next.js 14 (App Router) + TypeScript + Tailwind, self-hosted via Docker Compose + Caddy.

## Commands

```bash
pnpm install
pnpm dev          # next dev -H 0.0.0.0
pnpm build        # next build (standalone output)
pnpm start        # next start
```

Requires Redis for view counts. `REDIS_URL` defaults to `redis://redis:6379`
(the compose service name). For local dev outside Docker, run a Redis
container and point `REDIS_URL` at it (e.g. via `.env.local`, which Next.js
autoloads) — otherwise every request logs a connection error, though the app
still boots and degrades gracefully (views just don't update).

No test suite or lint script is configured in `package.json`; `.eslintrc.json`
extends `next/core-web-vitals`.

Production:

```bash
docker compose build
docker compose up -d
```

## Architecture

### Posts are files, not a database

Posts are `.mdx` files in `posts/`, named `YYYY-MM-DD-slug.mdx`, with
`title` / `date` / `tags` frontmatter. Dropping a new file into `posts/` is
enough to publish — `lib/posts.ts` scans the directory at request time, no
route registration or code changes needed. The filename's date is a fallback;
frontmatter `date` wins when present. `lib/posts.ts` also strips a leading
`# Title` H1 from the body unconditionally, since every post duplicates the
frontmatter title as its opening heading and the page header already renders
an `<h1>`.

Posts render through `next-mdx-remote/rsc` at
`app/(post)/[year]/[slug]/page.tsx` (routes are `/[year]/[slug]`, via
`generateStaticParams`). Static `.mdx` pages (e.g. `app/about/page.mdx`) go
through `@next/mdx`'s built-in pipeline instead. Both pipelines share one
component mapping — `mdx-components.ts` — so post content and static pages
render identically. Adding a custom MDX element (callout, tweet embed, etc.)
means adding a component under `app/(post)/components/` and wiring it into
that shared map, not duplicating it per pipeline.

### Style guide lives inside the post components

Every component under `app/(post)/components/` is both a piece of markup
styling *and* an entry in the MDX component map above — that directory is
the de facto style guide for post content. Pure stateless components
unrelated to post markup live under `./components` at the app root.

### Infra swapped from managed to self-hosted

- **Views**: `app/redis.ts` (via `ioredis`), replacing the original
  `@upstash/redis` REST client. `app/api/view/route.ts` reads/increments a
  `views` hash keyed by post slug.
- **Analytics**: self-hosted Umami (`app/analytics.tsx`), replacing
  `@vercel/analytics`. The tracking script is a no-op unless
  `NEXT_PUBLIC_UMAMI_WEBSITE_ID` is set.
- **Deploy**: push-to-deploy via a repo-scoped self-hosted GitHub Actions
  runner (`.github/workflows/deploy.yml`).

`app/redis.ts` stubs out the Redis client entirely during
`next build`'s static-generation phase (`NEXT_PHASE === "phase-production-build"`)
— that phase runs in CI and in the Dockerfile's builder stage, neither of
which has a real Redis, and neither needs one since views/tweet-embed
caching are read/written at request time, not baked into the static build.
At runtime, the real client uses `maxRetriesPerRequest: 3` and logs
(doesn't throw) on connection errors, so a Redis blip doesn't crash-loop the
app.

### Ambient background + ASCII art

`app/ambient-background.tsx` runs a full-viewport particle simulation
(adapted from `friend-enemy-dots.tsx`, an implementation of Simon Woods'
"Dancing with friends and enemies") behind all page content. The homepage
hero (`app/lain-portrait.tsx`) renders a Serial Experiments Lain-inspired
ASCII portrait generated by `scripts/ascii-art.py` (block-character
density-mapping) — regenerate via that script, don't hand-edit
`app/lain-ascii.ts`.
